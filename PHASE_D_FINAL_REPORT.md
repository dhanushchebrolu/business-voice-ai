## 11. Inbound call flow

Implemented exactly per the brief's diagram: webhook → signature verify →
`webhook_events` idempotency insert → resolve number by E.164 (`status =
'active'` only) → `checkTelephonyAccess` (full entitlement gate) → create
`call_logs` row (marked `failed` with a reason if the gate rejects, so
rejections are auditable, not silently dropped) → `routeToAgentRuntime`
handoff stub on `answered`/`in_progress` → `finalizeCallBilling` on a
terminal status.

## 12. Outbound call flow

`initiateOutboundCall` server function: auth → membership → `checkTelephonyAccess`
→ `walletCanAffordOutbound` → create `call_logs` (`status: initiated`) →
adapter dial → store `provider_call_id`. All later state transitions and the
real charge come from the provider's own webhook events, not this function —
so a client that disconnects immediately after calling this still gets
billed correctly once the call actually ends.

## 13. Webhook security

Every event: signature verified before the payload is parsed as JSON
(constant-time HMAC-SHA256 compare, mirroring `razorpay.server.ts`'s
`verifySignature`), then deduped via the pre-existing `webhook_events`
`UNIQUE(provider, event_id)` table before any side effect. Unconfigured
provider → `503`. Bad signature → `401`. Unparseable/unrecognized event →
`400`.

## 14. Idempotency implementation

Three independent layers: (1) `webhook_events` unique insert rejects a
replayed provider event outright; (2) the call state machine treats a
same-status event as a no-op; (3) `debit_wallet_for_call` is idempotent per
`call_id` (row-locked check-then-insert, **plus** a DB-level partial unique
index on `wallet_transactions(organization_id, reference) WHERE kind =
'call_usage'` as a second, independent guarantee) and `usage_records` has a
matching unique index on `(call_id, kind)`. A duplicate webhook cannot
duplicate a call row, double-debit a wallet, or double-count revenue.

## 15. Call state machine

`ALLOWED_TRANSITIONS` in `telephony-guard.server.ts` — e.g. `completed ->
in_progress` and `failed -> answered` are rejected outright
(`checkCallTransition` returns `ok:false`, logged, no write happens). Every
terminal state (`completed/failed/busy/no_answer/cancelled`) has an empty
transition list. Same-state repeats are always a no-op, keeping the machine
idempotent. This is enforced entirely server-side; there is no browser
write path to `call_logs` at all (see §7), so this is defense on top of an
already-closed door, not the only door.

## 16. Billing integration

No second wallet, billing or revenue system. Calls are priced from the
**existing** `pricing_rules` (`voice_minute` / `outbound_minute`, already
present with real values before Phase D) plus any
`organization_pricing_overrides`, rounded up to whole minutes. The real cost
is applied once, at call finalization, via `debit_wallet_for_call` into the
existing `wallet_transactions` ledger (`kind: 'call_usage'`), and mirrored
into `usage_records` (`kind: 'call'`) so the pre-existing
`getProfitAnalytics` admin dashboard picks up telephony revenue/cost with
**zero changes on its side**.

## 17. Wallet integration

Reused entirely — no parallel balance field, no second ledger. `wallet_balance()`
is unchanged; Phase D adds two service_role-only functions on top of it (§6).

## 18. Race-condition protection

`debit_wallet_for_call` and `wallet_can_afford` both take `SELECT ...
FOR UPDATE` on the organization row before reading the balance, so two
concurrent finalizations for the same organization serialize instead of
both reading a stale balance. Combined with the idempotency key, a retried
or duplicated finalize event cannot double-debit. **Known limitation**,
stated plainly: the pre-dial affordability check is advisory, not a hard
reservation — a burst of many simultaneous *new* outbound-call requests
could all pass the pre-check before any of them finalizes, since the real
cost isn't known until each call ends. This is normal prepaid-telecom
behavior (you bill the real usage after the fact), not a double-charge bug;
a hard per-call reservation would need a live provider to test against
meaningfully and is flagged as a follow-up, not silently glossed over.

## 28. Known limitations

- No hard wallet reservation for outbound calls (§18).
- The generic adapter's REST/webhook shape is this adapter's own documented
  contract, not any specific vendor's real API — wiring an actual provider
  means overriding 3 methods with that vendor's real endpoints.
- `provisionPhoneNumber`'s "purchase" path is untestable without a
  configured provider; the "attach an already-purchased number" path is the
  one that works today for every provider in `TELEPHONY_PROVIDERS`.
- §30's `platform_settings` "pricing.*" vs. `pricing_rules` mismatch
  (documented in `admin.pricing.tsx` since Phase C) is unchanged — Phase D
  deliberately used only the canonical `pricing_rules` path
  (`voice_minute`/`outbound_minute`, already present) and did not touch
  `platform_settings` or attempt to reconcile the two.
