## Migration review

- **Coverage.** Row trigger `BEFORE UPDATE OR DELETE` (`contacts_opt_out_guard`) and statement trigger `BEFORE TRUNCATE`. INSERT … ON CONFLICT DO UPDATE and MERGE updates go through the UPDATE trigger. INSERT needs no guard: an opted-out row already holds the (organization, phone) unique key, so re-adding fails. Not covered (by design, requires database-owner rights): `ALTER TABLE … DISABLE TRIGGER`, `session_replication_role = replica`, dropping the trigger.
- **Clear bypass.** Only the transaction-local setting `clickai.opt_out_reversal = 'allowed'`, set and reset inside the definer function. API roles cannot call `set_config` (pg_catalog is not an exposed schema).
- **Workspace deletion.** Allowed only when the organization row no longer exists (the ON DELETE CASCADE from `organizations`). Authenticated users have no DELETE grant on `organizations`.
- **Locking / concurrency.** Reversal takes `SELECT … FOR UPDATE` on the contact; a concurrent reversal waits and then finds nothing to do (no second audit row). A DELETE or UPDATE racing an opt-out re-reads the locked row before the BEFORE trigger runs, so it sees the committed opt-out and is refused. `suppressContact` only updates rows still `opted_out = false`, so retries are no-ops.
- **Atomicity.** The contact update and the `audit_logs` insert run in the one function call (one transaction); any error rolls both back. A pg test forces the audit insert to fail and checks the contact is unchanged.
- **Rollback** (`docs/production-rollback-20261118120000-contact-opt-out-guard.sql`): drops only the two triggers, the two guard functions, `reverse_contact_opt_out` (both signatures) and the migration row. Contacts RLS, grants, the unique key, the E.164 check and every other trigger are untouched. Expected effect: opted-out contacts become deletable/renumberable again and the Contacts page reversal stops working — so roll back the Worker first.

## Sarvam cohort (`sarvam_campaign` mode) — investigation only

From Sarvam's documented tool contracts (read-only; nothing enabled, written or called):

- **Exclude cohort** (`cohort_category=stop_file`): removes contacts _already on that campaign_, matched by phone or by `user_identifier`. ClickAI sets `user_identifier` to its own `campaign_contacts.id`, so an opt-out could be pushed as a one-row exclude cohort without relying on phone matching. It is asynchronous (poll until terminal) — attempts already queued or in flight in that window may still dial. ClickAI has no exclude-cohort code today.
- **Workspace DND list**: campaigns skip listed numbers automatically, but the Sarvam workspace is shared by every ClickAI customer, so a number added there is suppressed for all customers — not workspace-scoped. Not suitable as the per-customer mechanism; usable only as a deliberate platform-wide block.
- **Pause / cancel** stop the whole campaign.
- Conclusion: an uploaded cohort _can_ be updated after an opt-out (exclude cohort), but not instantly and not by current ClickAI code. Keep `KLYRO_DISPATCH_MODE` unset (sarvam_campaign disarmed) until opt-out → exclude-cohort is implemented and tested.

## Remaining risks

1. PostgreSQL behaviour (all of the database guard) is unverified until the 18 pg tests run.
2. Database-owner access can disable triggers or run the rollback.
3. An owner can delete their whole workspace; a new workspace starts with no opt-outs (different customer by design).
4. Inbound opt-outs never set `contacts.opted_out` (caller identity unverified) — they only suppress that call's lead.
5. `sarvam_campaign` mode cannot stop an uploaded cohort promptly (above).
6. Production has none of this until the migration and Worker are deployed; until then all earlier loopholes are open there.
7. The Contacts page reversal uses a browser prompt for the reason; not visually checked.
